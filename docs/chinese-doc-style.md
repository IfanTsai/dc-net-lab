# 中文技术文档排版规范

编写或修改中文文档、注释、README、设计文档、Issue、Pull Request 描述和用户可见文案时，遵循以下规范。

## 1. 基本原则

* 保持中文表达自然、准确、简洁。
* 中文内容使用中文全角标点。
* 英文、数字、代码和技术名词使用半角字符。
* 保持技术名词、产品名和品牌名的官方拼写。
* 不要为了满足排版规范修改代码、命令、URL、文件路径或外部系统要求的固定文本。

## 2. 中英文之间增加空格

中文与英文单词、缩写、产品名或技术名词之间使用一个半角空格。

正确：

```text
使用 Go 编写后端服务。
通过 BGP 学习 Leaf 发布的路由。
使用 Claude Code 分析项目。
该服务通过 REST API 对外提供能力。
```

错误：

```text
使用Go编写后端服务。
通过BGP学习Leaf发布的路由。
使用Claude Code分析项目。
该服务通过REST API对外提供能力。
```

以下情况不主动拆分或增加空格：

* 官方产品名，例如 `豆瓣FM`。
* 代码标识符，例如 `CreateServerRequest`。
* 文件名、路径、URL 和命令。
* 外部协议或系统定义的固定字符串。

## 3. 中文与数字之间增加空格

中文与阿拉伯数字之间使用一个半角空格。

正确：

```text
该集群包含 100 台服务器。
请求将在 30 秒后超时。
当前支持 3 种部署模式。
```

错误：

```text
该集群包含100台服务器。
请求将在30秒后超时。
当前支持3种部署模式。
```

数字内部不要插入空格：

```text
IPv4
HTTP/2
SHA-256
10.0.0.0/8
192.168.1.1
```

## 4. 数字与单位之间增加空格

数字与物理单位、存储单位、带宽单位或时间单位之间使用一个半角空格。

正确：

```text
链路带宽为 100 Gbps。
磁盘容量为 2 TB。
请求延迟为 10 ms。
超时时间为 30 s。
```

错误：

```text
链路带宽为 100Gbps。
磁盘容量为 2TB。
请求延迟为 10ms。
超时时间为 30s。
```

以下情况数字与符号之间不加空格：

```text
15%
90°
-20℃
```

对于项目中已有的单位风格，应优先保持仓库一致。例如仓库统一使用 `100ms` 时，不要仅为了排版批量改成 `100 ms`。

## 5. 中文使用全角标点

中文句子使用全角中文标点：

```text
，。；：？！、（）「」『』
```

正确：

```text
该接口支持创建、查询和删除操作。
请求失败时，应返回明确的错误信息。
核磁共振成像（NMRI）是什么？
```

错误：

```text
该接口支持创建, 查询和删除操作.
请求失败时, 应返回明确的错误信息.
核磁共振成像(NMRI)是什么?
```

全角标点与相邻文字之间不增加空格。

正确：

```text
服务基于 Go、MySQL 和 Kafka 构建。
请求失败时，返回错误。
```

错误：

```text
服务基于 Go 、MySQL 和 Kafka 构建。
请求失败时， 返回错误。
```

## 6. 英文内容使用半角标点

完整英文句子、英文标题和英文专有名称内部使用英文半角标点。

正确：

```text
他说：「Stay hungry, stay foolish.」
推荐阅读 Hackers & Painters: Big Ideas from the Computer Age。
```

错误：

```text
他说：「Stay hungry，stay foolish。」
推荐阅读 Hackers＆Painters：Big Ideas from the Computer Age。
```

中文语境中的英文短语结束后，仍根据外层中文句子使用中文标点：

```text
系统返回 `connection refused`，随后进入重试流程。
```

## 7. 不重复堆叠标点

不要连续堆叠相同的问号或感叹号。

正确：

```text
服务为什么启动失败？
该问题已经修复！
这种行为真的符合预期吗？！
```

错误：

```text
服务为什么启动失败？？？
该问题已经修复！！！
这种行为真的符合预期吗？！？？！！
```

技术文档应尽量避免使用感叹号表达强调。

## 8. 数字使用半角字符

使用半角阿拉伯数字。

正确：

```text
集群包含 1000 个节点。
```

错误：

```text
集群包含 １０００ 个节点。
```

不要在正文中使用全角英文字母或全角数字进行视觉对齐。表格对齐应通过 Markdown、CSS 或排版工具实现。

## 9. 专有名词保持官方大小写

技术名词、产品名、公司名和协议名必须使用官方拼写。

正确：

```text
GitHub
GitLab
JavaScript
TypeScript
Go
Vue.js
Node.js
MySQL
PostgreSQL
macOS
iOS
OpenAI
Claude Code
Kubernetes
Prometheus
Grafana
Kafka
BGP
VXLAN
```

错误：

```text
github
Github
GITHUB
Javascript
typescript
Golang
VueJS
nodejs
Mysql
MacOS
K8S
```

只有在代码、命令或官方名称本身如此定义时，才保留非标准大小写。

不要为了页面视觉效果直接改变正文中的标准大小写。需要全大写或全小写展示时，应在展示层通过 CSS 等方式处理。

## 10. 不使用生造或不规范缩写

除非缩写是行业通用、项目已定义或上下文中已经解释，否则使用完整名称。

推荐：

```text
TypeScript
HTML5
React
Next.js
frontend developer
Pull Request
configuration
documentation
```

谨慎使用：

```text
TS
FE
PR
config
docs
```

不推荐使用团队外难以理解的生造缩写。

首次出现不常见缩写时，应先给出完整名称：

```text
Service Level Indicator（SLI）
Border Gateway Protocol（BGP）
```

后续可以直接使用缩写。

## 11. 引号与书名

中文内容默认使用中文引号：

```text
「外层引用」
『内层引用』
```

示例：

```text
文档中提到：「请求失败后进入『指数退避』流程。」
```

仓库已经统一使用弯引号时，可以继续使用：

```text
“外层引用”
‘内层引用’
```

同一份文档中不要混用两套引号风格。

中文书名使用书名号：

```text
《计算机网络》
```

英文书名保留英文原名，优先使用 Markdown 斜体：

```markdown
*Designing Data-Intensive Applications*
```

不要将英文书名中的英文标点替换为中文标点。

## 12. 代码、命令和标识符

以下内容使用反引号包裹：

* 代码标识符
* 函数名和类型名
* 配置项
* 命令
* 文件名和路径
* 环境变量
* HTTP Header
* 状态值
* 短代码片段

示例：

```text
调用 `AllocateAddress` 分配地址。
执行 `go test ./...` 运行测试。
配置文件位于 `configs/default.yaml`。
通过 `HTTP_PROXY` 指定代理。
请求头使用 `Content-Type`。
状态必须为 `READY`。
```

反引号内部不得增加排版空格：

正确：

```text
调用 `CreateServer` 创建服务器。
```

错误：

```text
调用 ` CreateServer ` 创建服务器。
```

代码块中的内容必须保持原样，不应用中文排版规则。

## 13. Markdown 链接

链接文本按普通中文内容处理。

正确：

```markdown
请查看 [Go 官方文档](https://go.dev/doc/)。
```

不要为了在链接两侧制造视觉间隔而添加多余空格：

```markdown
请查看 [Go 官方文档](https://go.dev/doc/) 。
```

链接后的中文标点紧跟链接，不增加空格。

## 14. 标题规范

Markdown 标题应简洁明确。

推荐：

```markdown
## 地址分配流程

## BGP 路由传播

## API 错误处理
```

不推荐：

```markdown
## 地址分配流程。

## 关于 BGP 路由传播的一些说明

## API 错误处理！！！
```

标题通常不使用句号结尾。

标题中的英文和数字仍遵循中英文空格规范：

```markdown
## Go 服务启动流程

## 第 2 阶段部署

## BGP Session 状态管理
```

## 15. 列表与段落

列表项应使用完整、平行的句式。

推荐：

```markdown
- 验证请求参数。
- 查询可用地址池。
- 分配并持久化地址。
- 返回分配结果。
```

避免混用名词、动词和不完整短语：

```markdown
- 参数验证
- 查询地址池。
- 然后分配地址
- 返回
```

技术说明应优先使用连续、紧凑的段落。只有在表达并列项、步骤、检查项或参数时才使用列表，避免将每句话拆成独立列表项。

## 16. 技术文档中的例外

以下内容保持原始格式，不自动应用中文排版规则：

* 源代码和代码块
* Shell 命令
* SQL
* 正则表达式
* URL
* 文件路径
* IP 地址和 CIDR
* MAC 地址
* UUID
* Hash
* 配置键和值
* 协议字段
* 日志原文
* 错误原文
* 第三方接口返回值
* 用户明确要求保留的文本
* 自动生成文件

示例：

```text
`10.0.0.0/8`
`00:11:22:33:44:55`
`GET /api/v1/servers?id=100`
`failed to connect: connection refused`
```

不要修改引用的日志、报错和外部协议文本，除非用户明确要求改写。

## 17. Claude Code 执行要求

生成或修改中文文档时：

1. 自动检查中文与英文之间的空格。
2. 自动检查中文与数字之间的空格。
3. 自动检查数字与单位之间的空格。
4. 使用中文全角标点。
5. 保持完整英文内容内部的半角标点。
6. 检查专有名词的官方大小写。
7. 使用反引号标记代码、命令、路径和标识符。
8. 不修改代码块、日志、URL 和固定格式文本。
9. 优先保持仓库已有风格，避免产生大范围无意义格式 diff。
10. 当现有文档风格与本规范冲突时，只修改当前任务直接涉及的内容，除非明确要求全量格式化。

## 18. 输出前检查清单

输出中文文档前检查：

* 中文和英文之间是否有一个半角空格。
* 中文和数字之间是否有一个半角空格。
* 数字和单位之间是否符合项目规范。
* 中文句子是否使用全角标点。
* 英文句子内部是否使用半角标点。
* 全角标点两侧是否存在多余空格。
* 是否使用了重复问号或感叹号。
* 专有名词大小写是否正确。
* 代码、命令、路径和标识符是否使用反引号。
* 是否误改了代码块、日志、URL 或固定格式文本。
* 是否产生了与当前任务无关的大范围排版修改。
